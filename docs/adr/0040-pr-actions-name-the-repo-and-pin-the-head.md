# PR branch actions name the repository and pin the head commit

The desktop's merge box can merge a pull request, update its branch, close or reopen it, toggle draft, and delete or restore its head branch. Every one of these calls names the repository explicitly (`gh … --repo owner/repo`, or a REST path under `repos/owner/repo`) and none runs against the user's working tree. The head branch is deleted through `git/refs` rather than with `gh pr merge --delete-branch`.

`--delete-branch` is the obvious flag, and the reason it is not used is ADR 0020. Run inside a checkout, `gh pr merge --delete-branch` also deletes the local branch, switching to the base branch first if the deleted branch is checked out. A review tool that moves the user's HEAD after a click labelled "merge" is exactly the late-surfacing mutation 0020 exists to prevent, and the flag's behaviour depends on the `gh` version and on whether `--repo` was passed. Deleting the remote ref directly has one meaning everywhere.

A merge always carries `--match-head-commit`. On a PR Diff or remote PR view it is the head the on-screen diff was built from, so if the agent pushed again after the reviewer last looked, GitHub refuses the merge instead of landing commits nobody read; the box says so and disables the confirm until the diff is synced. A local-branch view shows the working tree, which has no PR head to compare, so there the live PR head is pinned and the box names it.

## Consequences

- "Delete branch after merge" is a second call after the merge, so it can fail on its own; the error says the merge went through. It runs only once GitHub reports the PR merged: on a repo with a merge queue, `gh pr merge` only enqueues, and deleting the branch then would drop the PR from the queue. On a base with a queue the box offers "Add to merge queue" with no method picker or delete option, since the queue picks the method and a delete would drop the PR from it, and shows a queued PR as queued. Deleting a closed PR's branch re-checks the PR's state live, since deleting the branch of a PR reopened in the meantime would close it again. A branch that is already gone counts as deleted, since a repo that deletes merged branches itself often gets there first.
- A branch is deleted only while it still points at the PR's head commit. A long-lived branch (`dev`, `staging`) can gain commits after its PR closed, and deleting it then would drop work no PR holds; Restore would bring back only the old head. Only GitHub's 422 for a missing ref counts as already deleted, since a 404 is also what a viewer without access gets.
- Delete and restore are offered for same-repo PRs only. A fork PR's branch lives in the fork, and GitHub reports the head repository as null once a fork is deleted. Falling back to the base repo would then target an unrelated branch that happens to share the name (`dev`, `patch-1`). Fork branches are managed on GitHub.
- Every request names the PR the card showed, and the backend refuses it when the active tab's PR differs. A confirm left open across a tab switch must not land on another PR with the same number.
- Repository merge settings (allowed methods, delete-on-merge, auto-merge, viewer permission) and a closed PR's branch existence are cached per key in the engine, not fetched on every 30s status poll. ADR 0026 explains why the loop's call volume matters. Auto-merge is offered only where the repo enabled it, which is off by GitHub's default.
