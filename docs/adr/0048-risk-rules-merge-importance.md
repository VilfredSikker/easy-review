# Importance and risk are one declared rule system

_Amends ADR 0036._

A reviewer had two rankings that answered the same question — what to read
closely — in two vocabularies: declared importance (`foundational`, `normal`,
`isolated`, ADR 0036) and the review's per-file risk (`high`, `med`, `low`).
The redesign shows one "File risks" list, so they are merged: **risk rules**
map a path, glob or file type to a tier `high | med | low | ai`, where `ai`
declares no tier and leaves the file to the AI review's rating. A path no rule
claims reads as `ai` too. ADR 0036's reasoning stands — the rules are declared,
generated by an agent with a distribution report, and hand-editable — only the
vocabulary and the table change.

## Where the rules live

Config stays global-only (ADR 0005). `[risk.<repo>]`, keyed by
`storage::rules_key`, holds a repo's **project** rules; `[user_risk]` holds the
user's own rules, applied in every repo. There is no repo-file source: the
"project rules" the design shows are the repo's table in managed config, not a
committed file, for the reason ADR 0036 rejected `.er/importance.toml`. A rule
may carry a label, the short reason a reader sees beside the file
(`"db/**" = { tier = "high", label = "Migrations" }`).

## Precedence

Within a table, ADR 0036's order: exact path, glob, file type, longest key
wins. Across tables, **source first**: the project table is searched to the end
before the user table, so a broad project glob beats a narrow user rule. The
project table is the one written about this repo; the user's is a general
preference, and letting it carve exceptions out of a repo's declared rules would
make one repo's ranking depend on rules written for every other. Defaults come
after every rule in both tables, so setting a project default cannot silently
switch the user's rules off. Both orders live in `config/risk_rules.rs` and
nowhere else.

## Reading the old table

A repo with only `[importance.<repo>]` reads it as its project rules:
`foundational` → `high`, `isolated` → `low`, `normal` → `ai`. `normal` maps to
`ai` rather than `med` because `normal` meant "nothing declared about this
path", and `med` would assert a judgement nobody made. Once a repo has a
`[risk]` table the old one is ignored, and the next write to that repo's rules
(the agent, or a Settings edit) carries it over and removes it, so a repo is
never left with two tables that disagree.

## Consequences

- Settings now writes rules (one rule per patch, validated; an unreadable tier
  or a pattern that does not compile is refused), which ADR 0036 left to hand
  edits and the agent. It goes through the same config save as every other
  setting.
- The `importance:` filter prefix, the agent's task kind and its JSON markers
  keep their old spelling: saved filters and queued tasks name them. They read
  the new tiers and the old ones.
- An `ai` file has no tier until a review rates it, and a view with no review
  (ADR 0004) shows it unrated rather than defaulting it to `low`.
