# Agent brief: epic <name>

Every implementer and reviewer agent reads this first. The epic's state lives on the Feature Board; the orchestrator exports what you need to a scratch folder and names it in your prompt: this brief (`BRIEF.md`), the plan with the owner decisions and the status table (`PLAN.md`), your PR's entry (`PR-<id>.md`) and the build log (`LOG.md`). Where a decision and the plan disagree, the decision wins.

Your prompt starts with a line `run: <run id>`. Leave it there: it is how the orchestrator counts your tokens.

## Ground rules

- **Base and target.** All work branches from and targets `<release>`, the epic branch. Never `main`.
- **Branch names.** Use `epic/pNN-<slug>`, as named in the plan.
- **Repo rules.** Follow root `CLAUDE.md`: `CONTEXT.md` vocabulary, the ADRs that touch your area, the lint gate that only tightens (ADR 0038), and `docs/agents/writing-docs.md` before editing a doc.
- **Scope.** Do exactly your PR's scope from your plan entry. When you find something outside it, note it in your report under "follow-ups" instead of fixing it.
- **The board.** Never write to the Feature Board, and never commit the exported files. Only the orchestrator updates the epic. Spec text, follow-ups and owner actions go in your report.
- **Production.** Never tag a release or publish to npm or crates. Anything that needs an external account goes in the PR body under **Owner actions**.
- **Model names.** Keep model names out of PR text and code; the only exception is the `Co-Authored-By` trailer.

## Workspace

- **Where to work.** The orchestrator gives you a worktree path, `<worktrees>/pNN`. Work only there. If it does not exist, create it with `git -C <repo> fetch origin <release> && git -C <repo> worktree add -b epic/pNN-<slug> <worktrees>/pNN origin/<release>`. Use `just` for builds and tests: it keeps the split target dirs.
- **Disk.** Each worktree builds its own cargo target dirs. Don't copy targets between worktrees; say so in your report if disk runs low.
- **Shared machine.** Other agents run at the same time. Never `pkill` or `killall` a pattern; stop only processes you started, by PID. Run heavy checks through `~/.claude/scripts/locked.sh <worktree> <command…>` in the foreground when that script exists. A timeout that happens only under load, in a file that passes alone, is not a failure: report the file.

## Verification before you push

- `just test` while working.
- `just ci` before the PR (format, clippy, UI lint, docs check, comments check, tests, headless engine build). CI runs it again on the PR.

Fix failures; never skip, disable or quarantine a test to get green. If a failure already exists on `<release>` and is unrelated, show that it fails there too and note it in the report.

## Commit, push, PR

1. **Commit** in small logical commits, each ending with the attribution lines your session gives.
2. **Push** with `scripts/safe-push.sh epic/pNN-<slug> <release>` (from the skill folder): it refuses a push that would rewrite history or that misses the epic branch's tip.
3. **Open the PR** on `VilfredSikker/easy-review` with base `<release>`. The title starts with `[Pnn]`. Keep the body short: what changed and why, and how to check it. Then add **Verification** (the commands you ran, with counts), **Call-outs**, **Owner actions** and **Follow-ups**. End the body with the PR attribution lines your session gives.
4. **Do not merge.** The orchestrator merges after review.

## Report back

Keep it short; the detail belongs in the PR body. Include the PR number and URL, branch and head SHA, verification results per command, call-outs, owner actions, deviations from the plan with the reason, follow-ups, and anything the next PR in the lane must know.

## Reviewers

1. **Read the diff:** `git diff origin/<release>...origin/epic/pNN-*`.
2. **Check it against the plan entry** and the repo rules.
3. **Look for** correctness bugs, panics and unwraps on user input, blocking work on the UI thread, missing tests, scope creep, rule breaks and missing call-outs.
4. **Re-run verification only for what you doubt.** Don't rebuild the whole workspace for a doc-only PR.
5. **Post one PR review** with event `COMMENT`: findings ranked by severity, each with a file:line reference, ending with the footer:

   ```

   ---
   _Generated by [Claude Code](https://claude.ai/code)_
   ```

6. **Report** a verdict of `merge`, `fix-then-merge` (with the must-fix items) or `rework`, and the findings.
